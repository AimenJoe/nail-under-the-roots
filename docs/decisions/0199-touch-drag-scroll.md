# 0199. 메뉴 목록을 손가락으로 끌어 굴리기 · 탭은 뗄 때

- 날짜: 2026-10-28
- 상태: 채택(v0.4.4 패치, 0193 갈래). 0198 "남은 것"을 한다.
- 사장: "터치스크린에서는.. 목록 같은 거 밑으로 스크롤하기 어려운데..? 어떻게 하지?" → 제안(끌어 굴리기 + ▲▼ + 도우미 하나) → "응 진행해"

## 무엇이 문제였나(코드 조사)
- 메뉴에서 터치는 **손가락을 대는 순간의 탭** 하나뿐이었다. 움직임·마우스 휠은 메뉴가 읽지 않았다(`input::read_touch`, `read_mouse`).
- 목록 대부분(설정·안내 주제·도감·개발 목록)은 저장한 창 없이 "커서가 창 맨 아래 줄"이라 보고 커서에서 창을 계산했다. 그래서 창은 커서가 가장자리를 넘을 때만 움직였고, ▲▼는 그림뿐 — 터치로는 가려진 줄을 볼 수 없었다. 저널·앨범은 저장한 창이 있었지만 따로 짠 코드. 같은 공식이 넷, ▲▼ 그리기가 여섯.

## 결정
- **입력**(`input.rs`): 메뉴 모드에서 짚은 손가락(`MenuFinger`)을 따라간다.
  - 움직이지 않고 떼면 **탭**(짚은 자리). 한 프레임 안에 짚고 뗀 짧은 탭은 바로.
  - 화면 높이의 3%를 넘게 움직이면 **끌기** — `Actions::drag`(화면 px, 위로 끌면 +: 아래 줄이 드러난다). 끌었으면 뗄 때 탭이 아니다.
  - 마우스 휠은 `Actions::wheel`(칸). 터치를 흉내 낸 가짜 마우스 클릭은 끈다(`simulate_mouse_with_touch(false)`) — 켜 두면 짚는 순간 클릭이 되어 끌기가 줄을 누른다.
  - 게임 모드(가상 스틱·버튼)는 그대로 누르는 순간.
- **도우미 하나**(`ui::ListView`): 보이는 첫 줄·줄 수·줄 높이를 기억한다. `window`(그릴 때: 키·패드 커서를 창이 따라간다), `scroll`(끌기 px·칸만큼 창을 옮기고 커서를 창 안으로, 줄 하나가 안 된 거리는 쌓고 방향을 바꾸면 버린다).
- **쓰는 곳**: 설정·안내 주제·도감·저널·개발 목록(`ListView`), 앨범(줄 단위 `ListView`), 상태 탭(픽셀 그대로 + 끌기 px). 앱이 프레임마다 `scroll_in`(논리 px 끌기, 칸 = 휠 + ▲▼)을 만들고 화면이 쓴다.
- **▲▼를 누를 수 있게**: 설정·안내·도감·저널(`Hit::Scroll(±1)`, 앨범·상태는 원래 됐다). 줄 칸과 겹치는 자리는 ▲▼가 이긴다.

## 왜
- 손가락으로 끌어 올리면 목록이 따라오는 것이 폰의 기본 몸짓이다. ▲▼만 두면 한 줄씩 눌러야 해 긴 목록(저널 열 넘음·도감)이 답답하다.
- 탭을 뗄 때로 옮긴 것: 끌기를 시작한 줄이 눌리면(설정 줄을 누르면 값이 바뀐다, 저널은 두 번 누르면 받는다) 굴리려다 엉뚱한 것을 바꾼다. 모바일 UI의 탭은 보통 뗄 때 정한다.

## 확인
- `cargo test`: `list_view_scrolls_by_drag_and_follows_cursor`(쌓이는 끌기, 끝에서 멈춤, 커서가 창 안으로, 키 커서는 창이 따라감).
- 헤드리스 Chromium 터치(CDP `Input.dispatchTouchEvent`): 타이틀에서 "설정"을 손가락으로 → 열림(뗄 때), 위로 끌기 → 돌아가기 줄이 드러남, 돌아가기를 손가락으로 → 타이틀.

## 사람이 볼 것
- 폰(웹·APK)에서 저널·도감·안내·설정을 끌어 굴리기, 끄는 거리 3%가 알맞은지(너무 쉽게 끌기가 되어 탭이 안 먹지 않는지), 굴리는 빠르기(1:1).
