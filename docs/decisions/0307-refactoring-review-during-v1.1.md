## 3. 찾은 것
### 가. 같은 사실이 둘 — 마을 상태를 손으로 맞춘다(R41)
- `village::State`의 칸은 **모두 기록(profile)에서 나온다**(`App::village_state`). 그런데 사거나 건넬 때마다 앱이 월드의 사본을 칸 하나씩 고친다:
  `v.decor[i] = true`(꾸미기·저널 보상), `v.traces[q]`(부탁), `v.lamps[i]`·`v.glow`·`v.tree_ready`(등불), `v.plots`·`v.blooms`(텃밭) — 일곱 군데.
- 빠뜨린 자리가 있다: **큰 나무에서 재주를 깨워 반딧불을 써도 우물 위 반딧불 단계(`glow`)가 그대로다**(마을에 다시 들어와야 바뀐다). `v.glow`를 쓰는 곳은 등불 건네기 하나뿐이다.
- `tree_ready`는 그리기 함수(`App::draw`, 마을 HUD)가 매 프레임 월드에 쓴다 — 그림이 상태를 고치는 자리.
- `village_state`는 `App`의 메서드라 시험이 없다(앱은 시험에서 못 만든다). 앨범의 다시 듣기는 이것을 부른 뒤 칸 셋을 덮어쓴다.

### 나. 마을 창 탭의 틀(R42)
- 탭 다섯(꾸미기·짐·등불·수첩·텃밭)이 같은 꼴을 되풀이한다: 줄 목록 만들기 → 왼쪽 목록 칸 → 고른 줄 → 오른쪽 자세히 칸. 칸 나누기 여덟 줄이 다섯 번.
- **입력과 그림이 줄 목록을 따로 만든다**(`decor_rows()`·`lamp_rows()`·`visible()`를 `update_*`와 `draw_*`가 각각 부른다) — KB가 "전에는 이랬다"고 적은 그 꼴.
- 거절·고맙다는 한마디가 손으로: `shop_msg = Some(..); sfx.play(Deny); return;`이 열 번 남짓.
- 포포의 웃는 얼굴을 **번역된 글을 견줘** 정한다(`tr(m) == s.decor_thanks || …`). 텃밭·등불의 고맙다는 말은 빠져 있어 심거나 거둬도 웃지 않는다. 쉼터 가게(`stage.rs:996`)도 같은 방식.
- 아래 안내 줄을 `std::ptr::eq(tabs, GARDEN_TABS)`로 고른다 — `const` 조각의 주소 비교는 언어가 보장하지 않는다(지금은 맞게 나온다). 안내는 탭 표의 칸이어야 한다.
- 이름이 낡았다: 텃밭 칸 번호를 `decor_cursor`가, 마을 창 전체를 `Scene::Decor`·`Hit::ShopItem`이 든다. 마을 창 상태 여섯(`decor_cursor`·`decor_tab`·`village_tabs`·`village_view`·`garden_crop`·`shop_msg`)이 `App`에 흩어져 있다.

### 다. 저장이 한 곳이 아니다(R43)
- 0269 R31은 "저장은 `App::save_profile` 한 곳"이었다. 지금 `app/`에 `crate::profile::save(&self.profile)` 직접 호출이 **19곳**(꾸미기·짐·큰 나무·저널 보상·반딧불 맡기기·꿈·캐릭터 고르기·설정 …).
- `save_profile`만 하는 일(Steam·Epic 업적 맞추기, 이번 런에 만난 이웃 적기)이 그 길에서는 빠진다 — 다음 `save_profile`까지 업적이 늦는다.
  기록 자체는 안전하다(개발 시나리오 막기는 `profile::put`의 sandbox가 아래에서 한다).

### 라. 이웃의 정체가 나란한 match로(R44)
- 이웃 하나(`Who`)가 다섯 군데의 match로 풀린다: `Who → Speaker`(`story::speaker`), `Who → Spot`(`lamp_spot`), `Spot → 초상화`(수첩 탭),
  `Spot → 스프라이트`(`draw_note_neighbor`)와 `Who → 스프라이트`(`sorted.rs`) — 같은 이웃을 그리는 코드가 둘 —, `Spot::neighbor()`.
- 지금 틀린 곳은 없다. 이웃을 더하거나 그림을 바꾸는 날 둘 중 하나를 빠뜨리기 쉽다.

### 마. 자주 고치는 긴 그리기(R45)
- `draw_sorted`(273줄): 방의 것·배우·**마을의 것 50줄**·위험물·그림자 패스가 한 함수. 마을 물건을 더할 때마다 여기와 `draw_one`(211줄)·`Drawable`을 연다(v1.1에서 `Crop`·`Flower`·등불).

### 바. `world.rs` 한 파일(R46)
- 시험 빼고 4,198줄, 함수 121개. 덩어리로 보면 타격 539·위험물 398·**가장 깊은 곳 377**(`deep_tick` 214줄 포함)·플레이어 325·적 281·연출 274·이야기 152.

## 5. 하지 않는 것
- **장면 스택으로 다시 짜기**(KB ①): 출시한 게임이고 흐름은 `flow`·`after`의 시험이 지킨다. 값에 비해 위험이 크다.
- **긴데 안 고치는 함수**(`dungeon::generate` 489줄 — 11월 10일 뒤 0번, `draw_enemy` 407줄, `draw_descent` 344줄): 길이만으로는 비용이 아니다(0230 R18). `generate`는 v1.2에서 새 지대의 굴 모양을 만질 때 그때 나눈다.
- **지대·길 표를 더 묶기**: `Biome`·`Leg`의 match는 `_`가 없어 다섯째 길·새 지대를 넣으면 컴파일러가 자리를 알려 준다(여덟 파일 남짓). 표로 더 모을 까닭이 아직 없다.
- **이웃 표 전체**(`characters.rs` 같은 한 줄 표): 이웃은 아홉으로 굳었고 갈리는 것이 대부분 글·그림이다 — R44의 "그리기 하나"까지만.

## 6. 추천 순서
1. **R41 → R43**(반나절 안): 버그 하나를 고치고, 두 "한 곳"을 되돌린다. 동작이 바뀌는 것은 우물 반딧불과 업적 시점뿐.
2. **R42**: v1.1을 닫기 전, 사장의 등불·텃밭 검토가 끝난 뒤(검토 중에 틀을 바꾸면 판정과 코드 변화가 섞인다).
3. **R45·R44**: R42의 준비로 그 앞에(R44가 탭의 그림 칸을 `Who`로 바꿔 둔다). R42를 안 하면 마을 그림을 다음에 만질 때.
4. **R46**: v1.1을 닫은 뒤, v1.2를 시작하기 전.
5. R47은 미룬다.

## 7. 대상 갈래
**`release/v1.1`에 바로, 작은 커밋으로.** 따로 리팩터링 갈래를 만들지 않는다.

| 갈래 | 이 일에서 | 까닭 |
|---|---|---|
| `release/v1.1` | **여기서 한다** | 작업 갈래(사장 2026-11-23). 고칠 코드의 절반(등불·텃밭 탭, 화단 그리기)이 여기에만 있다. push마다 CI(fmt·clippy·시험·연기 시험)와 개발판이 돈다 |
| `release/v1.0` | 건드리지 않는다 | PR #30(v1.0.1)이 MS Store 인증을 기다린다 — 여기에 커밋하면 나갈 1.0.1의 내용이 바뀌고, 이미 올린 상점 빌드(Epic `1.0.1-9b4480d`)와 어긋난다. 지금 v1.0은 v1.1에 다 들어 있다(v1.0에만 있는 커밋 0) |
| `main` | 건드리지 않는다 | 운영판. v1.1을 닫을 때 `release/v1.1 → main` PR로 함께 간다 |
| 따로 만든 리팩터링 갈래 | 만들지 않는다 | 오래 사는 갈래는 리팩터링을 막는다(아래 8절 Fowler) — 그 사이 `release/v1.1`에 들어오는 일과 합칠 때 부딪친다. 한 걸음 = 한 커밋이면 되돌리기는 `git revert` 하나 |

- **v1.0으로 되가져가지 않는다**: R41의 우물 반딧불은 v1.0에도 있지만 보이는 것뿐이고, R43의 업적 시점도 다음 저장에 따라잡는다. 1.0.x에 꼭 넣고 싶으면 1.0.1이 나간 뒤 그 두 커밋만 골라 옮긴다(따로 물을 것).
- **합치는 방향의 위험**: v1.0 패치는 v1.1에 합친다(0193). 파일을 나누는 R46 뒤에는 v1.0의 `world.rs` 패치가 저절로 합쳐지지 않는다(git은 파일 나누기를 따라가지 못한다) → **R46은 PR #30이 Merge된 뒤**에 하고, 그 뒤 v1.0 패치는 손으로 옮긴다고 `docs/release.md`에 한 줄.
- 세션의 지정 갈래(`claude/…`)는 쓰지 않는다 — 이 레포의 규칙(CLAUDE.md "갈래")이 먼저고, `release/v1.1` push는 된다(0307 커밋으로 확인).

### R41 마을 상태 = 기록의 함수
```rust

    pub fn of(p: &Profile, walking: Character) -> State { /* 지금 App::village_state 본문 */ }

// app.rs
fn sync_village(&mut self) {            // 기록이 바뀐 뒤 한 줄
```

- `tree_ready`(깨울 재주가 있나)도 기록에서 나온다 → `talents`의 순수 함수로 옮겨 `State::of` 안에서 부른다. 그리기 함수의 쓰기는 지운다.

- 시험(`village.rs`): 캐릭터마다 제 자리가 빈다, 등불 셋째 뒤 `lamps[i]`, 반딧불 수 → `glow`, 깨울 수 있으면 `tree_ready`, 텃밭·화단이 기록과 같다.

```rust
struct Row    { pic: VillagePic, name: String, right: String, dim: bool }
```

### 계획과 달라진 것
- **R43의 이름**: 설계는 "직접 저장을 `save_profile`로"였지만 `save_profile`은 **월드에서 만난 이웃을 기록에 적는다** — 월드가 그 기록의 것이 아닐 수 있는 자리(슬롯 창·기록 지우기·타이틀)에서 부르면 옛 월드의 도감이 섞인다(0264가 막은 그 일). 그래서 층을 둘로: `write_profile`(쓰기 + 업적)을 모든 저장이 지나고, `save_profile`은 런의 저장만.
- **개발 시나리오의 부탁·등불**: 기록 사본에 적는다(전에는 월드 사본만 고쳤다). 슬롯에는 안 쓰고 타이틀로 돌아오면 버린다 — "이번에만"은 같다. 등불 탭의 단계·반딧불이 개발 판에서도 실제처럼 바뀐다.
