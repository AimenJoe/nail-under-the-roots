# 0169. 코드 건강 점검: 확장·유지보수가 쉬운가, 어디를 리팩터링할까

- 날짜: 2026-10-27
- 상태: R1~R4 **구현**(2026-10-27, 사장: "R1부터 R4까지 순서대로 진행해. 구조적 결함을 최대한 가지지 않도록"). 결과는 맨 아래 "구현" 절. R5~R8은 제안으로 남는다. 사장: "우리 소스코드가 확장 및 유지보수가 용이한 구조인가? 리팩터링이 필요한 부분 없는지 분석해 주고, contribution 규칙과 배포에 대한 문서도 적어 줘." → 이 문서 + `CONTRIBUTING.md` + `docs/release.md`.
- 잰 것: 2026-10-27 v0.3.8 시점의 `src/`(Rust 45,469줄, 테스트 153개), `tools/`(Python 13,718줄), 워크플로 다섯, 결정 기록 168개, 나흘 동안 커밋 297개.

## 1. 한 줄 판정
**데이터 표로 넓히는 축은 좋고, 틱 한가운데(`World::step`)·앱·렌더의 거대 덩어리가 깊어지는 축이 약하다.** 새 적·무기·장신구·저널 목표·대사·시나리오·언어를 더하는 일은 표 한 줄이고 테스트가 지켜 준다. 반면 새 **메커닉**(흰 실 그물, 벽 쿵, 모으기 먼지 …)은 거의 매번 `World::step`(1,226줄)에 블록을 하나 더 쌓고, 그 함수는 `&Sfx` 때문에 단위 테스트로 돌릴 수 없다. 지금은 한 사람(+Claude)이 하루에 80~115 커밋을 내며 머릿속에 전체를 들고 있어 굴러가지만, 몇 주 쉬었다 돌아오거나 둘째 사람이 들어오면 여기서 막힌다.

## 3. 약한 곳(리팩터링 후보, 급한 순)

### R1. `World::step` 1,226줄 — 메커닉마다 쌓이는 한 함수 · 소리 때문에 테스트 불가
- 여덟 단계(플레이어 → 적·투사체 → 플레이어 공격 → 적 공격 → 겹침 → 정리 → 모험 → 웨이브)가 번호 주석으로만 나뉜다. 사이에 장치별 블록(문·천장·덤불·대장 소환·도토리·벽 쿵·모으기 먼지…)이 끼어 순서가 암묵적이다.
- `sfx.play(...)`가 51곳에 직접 박혀 있고 `self.sounds.push(...)`는 19곳 — **두 길이 섞였다.** `Sfx`는 테스트에서 못 만들어 `World::step`을 한 틱도 못 돌린다. 그래서 월드 테스트가 8개뿐이고(플레이어 19·적 16·모험 16), 테스트는 `thump_at`·`web_cut`처럼 부품 함수를 따로 부른다. 벽 쿵(0168)도 `Enemy`에서만 시험했다.
- 적이 쓰러질 때 하는 일(`kills += 1`·`deaths.push`·소리·터짐·실 풀림)이 **여섯 군데**에 복붙돼 있다.
- **제안**: (a) 소리는 전부 `self.sounds`(큐)로 — 앱이 틱 뒤에 비운다. `step(&mut self, a)`가 `Sfx`를 모르게 되면 **시나리오를 N틱 돌리는 테스트**가 가능해진다("적 다섯 종 방을 600틱 돌려도 panic 없음", "강타로 벽에 박으면 체력 -4"). (b) 단계를 메서드로: `tick_player`, `tick_enemies`, `apply_strike`, `enemy_attacks`, `hazards`(문·천장·덤불·지뢰), `cleanup`. 순서는 `step`에 여덟 줄로 남는다. (c) `fn kill(&mut self, i, cause)` 하나로 여섯 복붙을 모은다. 비용: 하루. 위험: 낮음(동작 그대로 옮기기 + 헤드리스 캡처 비교).

### R2. `World` 구조체 118개 공개 필드
- 싸움(enemies·projectiles·waves·cocoons·mines·clouds·rocks·webs), 손맛(feel·fx·sounds·toast), 이야기 깃발(clover_fight·petal_at·warren_open…), 가장 깊은 곳(deep), 마을 NPC, 모험(adv)이 한 평면에 있다. 무엇이 `RunSave`(쉼터 저장, 24칸)에 들어가고 무엇이 틱마다 새로 생기는지 구조체로는 안 보인다.
- **제안**: 묶음 넷 — `Arena`(싸움 상태), `Story`(런 깃발), `Deep`, `Juice`(feel·fx·sounds). 필드 이름은 그대로, 접근만 `w.arena.enemies`. R1과 함께 하면 `tick_enemies(&mut self.arena, …)`처럼 빌림이 좁아져 `let chief: Vec<_> = … collect()` 같은 우회가 준다. 비용: 반나절~하루, 거의 기계적 치환.

### R3. `render.rs` 6,976줄 · `draw_enemy` 340줄 · `draw_sorted` 337줄
- 한 파일에 월드·HUD·메뉴 화면·내려가기 전환·그림자·입자·조명이 다 있다(112 함수). 지금도 파일을 열면 어디를 봐야 할지 `grep`이 먼저다.
- **제안**: `render/` 폴더로 쪼갠다 — `world.rs`(정렬·타일·문·출구), `actors.rs`(플레이어·적·이웃), `fx.rs`(입자·빛·예고), `screens.rs`(메뉴·HUD·앨범·도감), `descent.rs`, `shadow.rs`. 함수 몸은 그대로, `mod` 선언과 `use`만. `draw_enemy`의 종별 `match`는 그대로 둬도 된다(표로 만들 만큼 규칙적이지 않다). 비용: 반나절. 위험: 거의 없음.

### R4. `app.rs` 3,551줄 + 67 필드, `App::start` 200줄
- 장면은 이미 `app/stage.rs`·`slots.rs`·`dream.rs`·`pick.rs`·`run.rs`로 나누기 시작했다. 남은 큰 덩어리는 메뉴 탭 여섯(상태·가방·저널·도감·지도·설정 — `draw_status` 169·`draw_bestiary` 167)과 타이틀·설정·조작 설정.
- **제안**: 같은 방식으로 `app/menu.rs`(탭 여섯), `app/settings.rs`, `app/album.rs`. `App::start`의 시나리오별 분기(33곳의 `Scenario::`)는 `scenario::build`로 더 내려보낸다(월드를 만드는 일은 거기, 앱 상태 초기화만 남긴다). 비용: 하루.

### R5. `Enemy::update` 422줄 — 13 행동이 한 `match`
- 종을 더할 때마다 이 함수에 팔이 자란다(`Behavior::` 46곳). 상태 기계 자체는 좋다.
- **제안**: `enemy/behavior/{chief,momo,doto,kongi,clover,mobs}.rs`에 `fn tick(e: &mut Enemy, ctx: &Ctx) -> Option<State>`로 행동만 뺀다. 공통(넉백·마찰·벽·벽 쿵·독·경직)은 `update` 머리·꼬리에 남긴다. 비용: 하루. R1보다 급하지 않다 — 새 종은 자주 안 더한다(0146 이후 없음).

### R6. `i18n.rs` 8,438줄(712키 × 11언어, 구조체 한 개)
- 키가 구조체 필드라 **빠진 번역 = 컴파일 에러**인 건 큰 장점이다. 버리지 말 것. 문제는 한 파일이라 글 한 줄 고치면 8천 줄 파일을 여는 것, 그리고 머지 충돌.
- **제안**: `i18n/mod.rs`(구조체·`Tr`·`fill`)와 `i18n/{ko,en,ja,zh_hans,pt_br,fr,es,de,ru,zh_hant,pl}.rs`로 언어별 파일. 구조체는 그대로. 실행 시간 맵으로 바꾸지 **않는다**(컴파일 검사를 잃는다). 비용: 한 시간(기계적).

### R7. 통합 시험이 레포 밖에 있다
- 눈으로 확인하는 헤드리스 Chromium 스크립트(개발 시나리오 진입 → 조작 → 스크린숏)는 매번 세션 임시 폴더에 쓰고 버렸다. 레포에는 `tools/site/shots.js`(공식 페이지 스크린숏)뿐이다. 세션이 바뀌면 다시 쓴다.
- **제안**: `tools/test/smoke.js` 하나 — 타이틀 → 개발 시나리오 몇 개(적 다섯 종·토끼풀·마을·가장 깊은 곳) → 정해진 입력 → 스크린숏 + 콘솔 panic 검사. `deploy-web.yml`의 PR 단계에서 돌릴 수 있다(러너에 Playwright 설치 1분). R1이 되면 같은 것을 Rust 테스트로도 돌린다.

### R8. 작은 것들
- `cutscene.rs`가 `crate::app::{STONE_CLAW, SPROUT_CLAW}`를 본다(아래층이 위층 참조). 상수를 `equipment.rs`로 옮긴다. 10분.
- 저장 형식 호환 시험이 없다: `profile.rs`·`suspend.rs`·`prefs.rs`에 "v0.3.x가 쓴 문자열 고정 샘플을 읽어도 같은 값"이 없다(테스트 8개는 왕복만). 형식을 바꿀 때 제일 무서운 곳이다. 샘플 셋 넣기 한 시간.
- `tools/art/illust.py`(1,694줄)·`portraits.py`(1,648줄)의 코드 그림은 나노바나나 원본으로 대체돼 `title_fog`·칸 4 말고는 쓰이지 않는다. 지우거나 `legacy/`로 옮기고 `docs/art/cutscene-illustrations.md`만 남긴다. 레포가 정직해진다.
- `CLAUDE.md`(61줄이지만 한 줄이 수백 자)는 규칙과 "어디에 뭐가 있나"가 섞여 읽기 힘들다. "어디에 뭐가 있나"는 `docs/architecture.md`(모듈 지도·틱 순서·표 목록)로 빼고 `CLAUDE.md`는 규칙만. 지금 `CONTRIBUTING.md`가 그 첫걸음이다.
- 워크플로: `build-android.yml`·`build-ios.yml`이 **모든 브랜치 push**마다 돈다. 작업 브랜치 커밋이 하루 100개면 APK·iOS 빌드도 100번이다. `main`과 태그·수동으로 줄이고, 브랜치 빌드가 필요하면 `workflow_dispatch`. 10분.

## 4. 하지 않을 것
- ECS·플러그인·동적 디스패치로 다시 짜기. 지금 구조(상태 기계 + 표)는 1인 액션 게임 규모에 맞다. 문제는 **함수·파일 크기와 테스트 가능성**이지 아키텍처가 아니다.
- `i18n`을 실행 시간 맵·JSON으로.
- 렌더와 월드 사이에 추상 계층(뷰모델) 넣기. 렌더가 월드를 직접 읽는 건 괜찮다(읽기만 한다).

## 5. 순서 제안
R8(상수·워크플로, 20분) → **R1**(소리 큐 통일 + 단계 메서드 + kill 하나, 하루) → R2(묶음, 반나절) → R3·R4(파일 쪼개기, 하루) → R7(스모크 시험, 반나절) → R6·R5·저장 샘플은 손댈 일이 생길 때. 각 단계는 **동작을 바꾸지 않는 커밋** 하나씩, 헤드리스 캡처 전후 비교로 확인한다. 기능 작업과 섞지 않는다.

## 확인
- 숫자는 전부 이 커밋에서 `wc`·`grep`·`awk`로 잰 것. 리팩터링 비용은 추정이다.
- 사람이 정할 것: 어디까지 할지(R1~R4를 추천), 언제(판정 F 뒤가 자연스럽다 — 0.4.0 전에 코드를 흔들지 않는다).

- R4에서 계획과 다른 것: `App::start`의 시나리오 분기를 `scenario::build`로 내리지 **않았다**. 분기는 거의 기록(프로필)·설정에 달린 것이라 `scenario.rs`가 프로필을 알게 되는 쪽이 더 나쁜 결합이다. 대신 "기록이 월드에 주는 것"을 `seed_run_from_profile` 한 메서드로 모았다.
- 자식 모듈 방식: `render/`·`app/` 자식은 `use super::*;`(부모의 가져오기·비공개 항목을 함께 씀), 부모는 `use <자식>::*;`로 모아 서로 보인다. 밖에서 쓰는 것만 `pub use`. 자식 안의 항목은 `pub(super)`.
- 확인: 네 커밋 모두 fmt·clippy(dev 포함)·wasm·Android·iOS·테스트 155개 통과. 헤드리스 캡처 전후 비교는 하지 않았다(무작위 입자라 픽셀 비교가 안 된다) — 대신 시나리오 통째 시험이 틱 흐름을 지킨다.
- 남은 것: R5(적 행동 파일별), R6(i18n 언어별 파일), R7(스모크 시험을 레포에 — Rust 쪽은 R1로 들어갔고 브라우저 쪽이 남음), R8(저장 형식 샘플 시험, 안 쓰는 코드 그림, 워크플로 트리거).
